1 · Why this exists

Phase 12 (docs/plan.md, "On-demand routes") replaced a fixed list of routes with routes drawn at the moment someone asks. R1–R5 built the new path: the pack (the routable network exported as arrays), the engine in shared/routes/, OutingIntent, and the planner. But the old path stayed alive beside it. Until this branch, the backend had two answers to the same question:

  • "a 15 km loop near Lecco" could decompose to loop_search, which filtered the 627 pre-generated (:Route) nodes in Neo4j (the catalogue), or to outing, which drew a fresh loop over the pack. Which one ran depended on how the model read the sentence.
  • The pipeline still carried the pgRouting loop factory that minted the catalogue, a bulk loader for it, and a GDS (Neo4j Graph Data Science) routing endpoint nobody called.

Two paths meant two sets of numbers for one ask, two sets of prompt rules to keep apart, and about 4,600 lines to keep green. R7 deletes the old path. What was impossible before: saying "every route a user sees was drawn by one engine, from one network, under one set of invariants". The branch also had to decide, piece by piece, which parts of the old path were in fact holding up something still alive — three of them were.

Key takeaways

  • R7 is a deletion: net about −4,650 lines across backend, pipeline and tests.
  • After it, the model has one way to ask for an outing, and the planner is the only thing that makes a route.
  • Three things the plan said to drop were kept, because each still carries a live feature: Intersection/CONNECTS_TO, the GDS plugin, and catalogue.route in PostGIS.

2 · The system, and where the work lands

Fig. 1 — The serving path after R7. Struck-through text is what the branch deleted; coloured boxes are what it changed or deliberately kept. Supabase (chat history, quotas) and the eval harness are omitted: R7 changed neither, except for the golden fixture and ledger lines.

Key takeaways

  • A route reaches a user one way only: planner draws it over the in-memory pack.
  • Neo4j is now a reader of routes that were kept (favourites), not a store of routes that might be shown.
  • The catalogue survives in exactly one role: the ground truth that the parity test checks the engine against.

3 · CHAT · One vocabulary for an outing CHAT

Goal. Take LoopSearchIntent out of the union the model fills, so that "loop" stops being a separate kind of ask and becomes a shape of an outing. Every piece of Python that existed only to serve the catalogue answer goes with it: catalogue_view, outing_view, merge_loops, widen_narrow_band, the orchestrator's catalogue block, and _cross_overlay. The prompt then has to draw the line between outing and trail_search on its own — and the golden eval showed that the first version of that line was wrong in three ways.

Fig. 2 — One outing turn after R7. The quota check, the answer-writing model call and the gateway hop are omitted; R7 did not change them. The dashed arrow is the no-pack refusal, which production cannot reach.

3.2 · Decisions, and why

  • ①The loop is a shape, not an intent. The rejected alternative was to keep loop_search in the schema and route it to the planner. That keeps two field vocabularies for one thing (max_distance_m on one, max_distance_km on the other) and a prompt rule to choose between them that decides nothing. The cost is that the outing/trail boundary is now a prompt rule with no fallback — which is why ⑤ took three commits.
  • ②No pack means a refusal in words. An empty list would be read as "no such route exists", which is false. REQUIRE_PACK makes this unreachable in production; it exists for dev and CI backends booted without PACK_DIR.
  • ③_cross_overlay was deleted, not ported. It bridged two intents that shared field names. OutingIntent spells its limits differently (km, hours), so a bridge would be new unit-converting code, not a deletion. The cost: "shorter" against a standing outing works only if the model emits an outing delta. If it emits a trail delta instead, the standing outing is redrawn unchanged and a trail search runs beside it. Golden g27 and g49 cover the happy case; nothing pins the failure case (Rec. 7). The typed chips avoid the model entirely.
  • ④The wire value stays "loop_search". Renaming it would touch the frontend types, conversations.ts and three test files for no change in behaviour. The cost is a name that describes a mechanism that no longer exists.
  • ⑤The gate tests for a shape or a trigger, never a noun. The first wording ("an OUTING TO GO AND DO") let the model classify by the word outing: "una gita a piedi di due ore" became an outing while "a two hour mtb ride" did not. Written as a strict binary, it then pulled descriptive asks away from semantic_theme (g05, g06). And the "never carry X from an earlier turn" rule listed distance, duration, difficulty and feature but not place, so g32 copied Bergamo into a fresh ask — R7 made that bite because the standing plan now holds outing.area, a more visible field than loop.near. Each fix was checked against the golden run before the next.
  • ⑥Drawn ids are still written to result_refs. Unchanged by R7, but its meaning changed: see §6.

3.3 · For a scalable system

The real change in load: asks that used to be an indexed Neo4j filter ("a 15 km loop") are now a draw. The draw is CPU work in the backend process, run through asyncio.to_thread on the default thread pool, measured at 165 ms median for a loop on the dev machine — the VPS number R2 owes is still owed, and it now matters more, because every loop ask pays it. The ceiling is the thread pool sharing one Python process and one GIL (the global interpreter lock, which lets only one thread run Python at a time); the upgrade already named in docs/route-design.md is a ProcessPool sized from that measurement. The per-conversation document cache (OUTING_CACHE_CONVERSATIONS = 50, in process) is R4's and unchanged.

3.4 · Security

The LLM boundary got smaller, not different. One fewer schema the model can fill, and no template name or id in any of the remaining ones. The no-pack refusal is fixed Python text, so it cannot echo user input. The adversarial half of check_intents_live is 7/7 clarify against the final prompt (441b401).

Key takeaways — CHAT

  • One way for the model to ask for an outing; the loop is its shape.
  • The outing/trail boundary lives in the prompt, and cost three golden-driven fixes. Final golden: 62/63, the baseline median.
  • g47 ("voglio camminare") is the one open entry, left unfixed on purpose — see Rec. 8.

4 · GRAPH · GDS leaves the serving path GRAPH

Goal. Delete every Neo4j template the catalogue needed, and every serving-path use of GDS. The plan (docs/plan.md R7) also said to drop the Intersection and CONNECTS_TO loads. That line assumed A-to-B routing died with POST /routes. It does not: /chat's RouteIntent ("how do I get from Lecco to Abbadia") walks those edges with plain Cypher. So the branch kept them, with the owner's confirmation.

Fig. 3 — Callers of the routing graph, before and after. The backend's serving path no longer reaches GDS at all; the only GDS caller left is an operator script.

4.2 · Decisions, and why

  • ⓐPOST /routes is deleted. It resolved two POIs, snapped them, and ran Dijkstra over a per-request GDS projection. Nothing called it — not the frontend, not a script; the gateway proxies the /routes prefix whole, so it was publicly reachable while unused. With it went route_gds_dijkstra, intersection_locations, route_edge_details, the smoke script, and most of test_api_routing.py.
  • ⓑIntersection/CONNECTS_TO stay. The plan's drop list was written assuming A-to-B went with the endpoint. It did not, and dropping the loads would delete a live feature's data. Worth knowing about what stays: shortestPath in Cypher minimises hops, not metres; total_m is summed afterwards and only used as a cap (Rec. 4).
  • ⓒThe GDS plugin stays, for a diagnostic. scripts.check_graph_connectivity projects the routing graph and runs WCC (weakly connected components) to find islands — the check that found fragility #9 (1,627 components). R7 is a retirement, not a place to lose a working check. The heap was cut to 1 GB, since it was sized for per-request projections.
  • ⓓroute_card and routes_by_ids survive. Favourites and resume hydrate through them, so a saved card and a live card cannot come to differ. What changed is what they find: in a fresh database, only routes someone saved. A database loaded before R7 still holds the 627 catalogue (:Route) nodes, because nothing deletes them — which is also what keeps catalogue-era favourites alive (Rec. 5).

4.3 · For a scalable system

The serving path lost its heaviest Neo4j call: a GDS projection per POST /routes request (the full projection was 92 MiB). What is left is bounded Cypher. The remaining ceiling is shortestPath itself: unweighted, depth-capped at 100 relationships, and run once per RouteIntent (the composer caps routes per turn). Two named places more than 100 junctions apart return no_path even when connected. The upgrade, if A-to-B grows, is to answer it from the pack like everything else, and drop CONNECTS_TO then.

4.4 · Security

One public route fewer: POST /routes took two free-text place names from any authenticated caller and started a graph projection, a cheap way to make Neo4j do expensive work. It is gone. What remains open is the procedure allowlist: gds.* is allowlisted and unrestricted on the same Neo4j the backend serves from, for the sake of an operator script. The backend calls no gds.* procedure, and every template passes the guard tests in tests/test_query_loader.py (no writes, bounded, no semantic edges in a path), so the exposure is defence-in-depth only. It should not reach production (Rec. 6).

Key takeaways — GRAPH

  • The serving path never calls GDS. The only caller is an operator diagnostic.
  • Three plan items were kept on purpose because they hold live features: the routing graph, the plugin, and the card templates.
  • The A-to-B walk is hop-shortest. That is pre-existing, but it is now the only one.

5 · ORACLE · The generator goes, the oracle stays ORACLE

Goal. Delete the pgRouting loop factory (draw/generate.py, draw/emit.py) and the bulk loader (export/neo4j_load.py, catalogue.cypher), without losing the one thing the catalogue still does: prove the engine right. Ratified decision ① of Phase 12 is "no human review before a user sees a route", and what makes that acceptable is the parity test — the new engine must reproduce all 627 catalogue ids from the same asks.

Fig. 4 — The oracle after R7. catalogue.route is no longer needed for the test to run, only to regenerate its fixture. The ⚠ is Rec. 3.

5.2 · Decisions, and why

  • ⓔThe 627 asks became a committed fixture. They used to be gitignored under pipeline/packs/, which was fine only while catalogue.route could be dumped again on demand. 190 KB in git is cheap insurance on the test that lets drawn routes ship unreviewed. catalogue.route stays in PostGIS as its source; it was never on R7's drop list.
  • ⓕThe engine's tests moved in with the engine. test_draw, test_destinations, test_ids imported only vaivia_routes. They sat in pipeline/tests/ because the code used to live there; the R2 re-export shims were the last thing that made that look deliberate (pipeline 273 → 229, shared 32 → 76, same total).
  • ⓖThe row mapping outlived its loader. vaivia_routes.neo4j_rows is what the favourite path writes with, so test_neo4j_load keeps testing it; only the bulk loader's own parser tests went.

5.3 · For a scalable system

The oracle is frozen at one network. The fixture names vertices by id, and CLAUDE.md is explicit that vertex ids do not survive a rebuild. So the moment the network is rebuilt — any topology repair, any new region — the parity test either crashes on a missing id or quietly replays asks from different junctions. Today that is survivable because pack-parity is kept aside. It stops being survivable when catalogue.route is finally dropped, because then the fixture cannot be regenerated either. Rec. 3 has the fix.

Key takeaways — ORACLE

  • No pipeline code mints routes any more; the pack engine is the only drawer.
  • The parity oracle no longer needs catalogue.route to run — only to be regenerated.
  • It is tied to one pack build by vertex id, and says so only by crashing.

6 · The route id, and what holds it now

The id is geometry-derived (vv2- + digest, vaivia_routes.ids.route_id) and is the one key every layer shares: the card, the document file name, the (:Route) node, the favourites row, and messages.result_refs.loop_ids. Before R7, most ids a user saw had a (:Route) behind them, because most loop answers came from the catalogue. After R7, only saved ones do. The same id now resolves differently depending on where you ask:

HolderWritten whenResolves after a restart?
SSE card (inline line)every answer—, it is the live answer
orchestrator _outing_docsevery answer, in processno — lost; a later favourite 404s (R4's accepted ceiling)
messages.result_refs.loop_idsevery answerno, unless saved — by-ids returns it as missing
document file + (:Route)on favourite onlyyes
(:Start {vertex_id})on favourite onlywrong after a pack rebuild — fragility #18

The query the id was built to enable is resume: one hydration call for the whole conversation.

frontend/lib/conversations.ts:50–53, 101–103 — resume keeps what by-ids returns and drops the restCHAT
const loops = (row.result_refs?.loop_ids ?? [])
  .map((id) => byId.get(id))
  .filter((loop): loop is Loop => Boolean(loop));
…
const wanted = [
  ...new Set(rows.flatMap((row) => row.result_refs?.loop_ids ?? [])),
];

So a resumed conversation now comes back as prose with no cards, except for routes the user saved. The code comment above it still says an id drops out when "its route left the catalogue". Nothing is wrong in the sense of a crash — the design rule "kept only when kept" is being followed — but the user-visible behaviour of resume changed, and nothing says so (Rec. 1).

backend/graph/save_route.cypher:32–42 — the one pack-local key that persistsGRAPH
// name: save_route_start
MERGE (s:Start {vertex_id: $row.vertex_id})
ON CREATE SET s.car_free = $row.car_free,
              s.names = $row.names,
              …
              s.location = point({longitude: $row.lon, latitude: $row.lat})

Fragility #18 was written on this branch: after a pack rebuild, the same vertex_id names a different junction, and ON CREATE means the stale node silently wins. docs/fragilities.md #18 has the rule; it has no fix yet.

Key takeaways

  • The route id is stable everywhere; what it points at is not — only a favourite makes it durable.
  • Resume lost its cards for every unsaved route. That follows from the design, but the UI does not say it.
  • (:Start {vertex_id}) is the last pack-local key in Neo4j, and it goes stale on rebuild.

  1. Resume shows no cards for unsaved routes, silently. Every loop_ids entry of an unsaved drawn route comes back missing from /routes/by-ids, and toChatMessages drops it. Persisting every drawn document would break "kept only when kept". Cheaper and honest: when a resumed assistant turn had ids and none hydrated, render one line ("These routes were drawn for that moment and not saved — ask again to redraw"). Fix the stale "left the catalogue" comment at frontend/lib/conversations.ts:34–38 in the same change.
  2. Stale catalogue wording in live code, two of them operator-facing. api/main.py:96 logs "outing asks answer from the catalogue" — false since f408733; they refuse. core/config.py:55 says the same. api/routes/routing.py:53–54, 72–74, 104–105 tell an operator to "reload the catalogue", with a loader that no longer exists; :149 cites search_loops and :168 cites catalogue.cypher, both deleted. core/config.py:41–44 loop_near_radius_m has no reader left. One chore: commit.
  3. The parity fixture is tied to one network by vertex id. Store the pack run_id it was dumped against (pack-parity) in the fixture, and have the test skip with that message on a mismatch rather than raise KeyError. Longer term, key starts by start_lon/start_lat (already in the fixture) and destinations by destination_id, and snap at test time — then the oracle outlives both the network and catalogue.route.
  4. route_between_intersections is hop-shortest, not metre-shortest. Cypher's shortestPath ignores distance_m; it is only summed afterwards. A longer path with fewer junctions wins. Either say so in the template comment and the answer ("a connecting path", not "the shortest"), or move A-to-B onto the pack's Dijkstra and drop CONNECTS_TO — which would also finish the R7 line as written.
  5. Old catalogue nodes are still in any pre-R7 Neo4j. Nothing deletes the 627 (:Route) nodes or their documents, and they are what keeps catalogue-era favourites alive. The plan's R7 "landed as" note does not mention it. Decide and write it down: keep them until favourites are migrated (what happens today, by accident), or delete them and let those favourites read as missing.
  6. GDS is unrestricted on the serving Neo4j for an operator script. Accepted for dev, because no backend path calls gds.* and the template guards hold. For D2 (compose.prod.yml): leave GDS out of the production Neo4j entirely, and run check_graph_connectivity against a dev copy.
  7. Nothing pins the _cross_overlay failure case. g27 and g49 check that "shorter" tightens outing.max_distance_km; add the expectation that no search rides along, so a model that emits a trail delta against a standing outing fails the golden instead of redrawing the old outing beside a trail search.
  8. g47 is open. Left unfixed on purpose in 441b401: the mechanism is known (only_activity() needs every other field at its default) but which field the model sets is not visible. Next time it fails, run eval_golden --only g47 with the composed plan printed; the answer decides prompt fix versus guard fix. g41 forbids simply loosening the guard.
  9. chat/compile.py:202 and :214 offer "three days hut to hut in the Orobie" as a suggestion in the coverage refusal — a multi-day trek the planner then refuses (R6 dropped). Swap in a single-day ask. Pre-dates R7; found while reading.
  10. results.kind = "loop_search" names a path that no longer exists. Accepted, because renaming touches the frontend types, conversations.ts and three test files for no behaviour change; rename it the next time the result contract changes for a real reason.
