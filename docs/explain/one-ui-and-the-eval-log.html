1 · Why this exists

Two things were impossible before this session, and one was invisible.

Impossible: using VaiVia on a phone. The frontend was a desktop two-pane shell — a 400px chat column beside a map that was always on screen — with a single 900px breakpoint that stacked the panes into 1fr 40vh. On a 360px screen that gave a cramped transcript above a strip of map too small to read a route from. The owner's decision (2026-08-28) was to stop treating mobile as a narrower desktop: one layout at every width, the conversation as the base layer, the composer permanently on the bottom edge, and the map as something that comes up when you tap a route and goes back down when you are done. Google Maps is the reference: the map is not the page, it is a thing you summon.

Impossible: saying which question regressed. eval_golden appended one aggregate line per run — {"decomposition": [50, 50], "retrieval_hit": [18, 20], …}. When retrieval moved from 19/20 to 18/20 the log said a number changed and nothing else; finding out which entry meant paying for another full run and reading 50 lines of console. The eval-pipeline doc named this as the first thing to fix, and Phase 8 E0 is the fix.

Invisible: the colour was carrying meaning nobody asked for. A 2026-08-27 amendment had spent the brand's one spare colour on a four-band difficulty ramp (lime / amber / flare / muted), with every mtb route drawn near-black. The owner's call this session was blunter and better: every route line is lime, and selection — the only thing the map actually needs to say — is width and opacity.

The session also extended docs/plan.md from seven phases to eleven. That is §3; the code is §4–§7.

Key takeaways

  • The UI change is not responsive CSS: it is a different model of what the map is.
  • The eval change is small and cheap, and it is what makes every later eval run legible.
  • Both were ratified by the owner before any code was written; the plan records the decisions.

3.1 · Decisions, and why

  • ①Phases append, they never renumber. Phase 7's items stay P0–P8; the new phases use E/D/F/U prefixes. A plan whose identifiers move is a plan whose git history stops matching its own cross-references.
  • ②Recommendations are marked, not silently adopted. Every choice the designers made that the owner has not ratified carries (recommended) inline and appears in a numbered list at the end of the plan. Thirty-five of them; fourteen gate Phase 10, which is why no factory code was written this session.
  • ③Edits were applied bottom-up. The deploy section inserts ~120 lines in the middle of the file, which invalidates every later line anchor. Appending the phases first, then editing upward, meant every anchor was still valid when it was used.

Key takeaways

  • Phases 8–11 are ratified in structure; Phase 10's parameters are not, and that is deliberate.
  • The plan now carries the branching and release rules that previously lived only in CONTRIBUTING.md.

4 · U0 · One colour on the map P11

Goal. Remove difficulty from the map's colour vocabulary entirely. The map answers one question — which route are we talking about? — and answers it with width and opacity.

frontend/components/MapView.tsx:120–135 — the whole line style, afterP11
// Every route line is lime (BRAND-SPEC amendment 2026-08-28). The
// picked route is wider and full-opacity; its siblings dim. Colour
// never encodes difficulty or activity: selection is the only thing
// the line says, and it says it with width and opacity. No casing
// (owner decision 2026-08-27). The layer is created once and
// restyles through setData — the expressions are all data-driven.
instance.addLayer({
  id: 'selection-line',
  type: 'line',
  source: 'selection',
  paint: {
    'line-color': token('--vv-lime', '#CCFF3B'),
    'line-width': ['case', selected, 4, 2],
    'line-opacity': ['case', selected, 1, 0.4],
  },
  layout: { 'line-cap': 'round', 'line-join': 'round' },
});

What came out with it: a five-arm match expression on properties.difficulty_band; the bands ref in ChatPanel and its three writers; loopBand, trailBand, bandOfRank and the DifficultyBand type from lib/difficulty.ts (SAC_ORDER stays — the card's difficulty squares still rank on it); the bands parameter of drawableFeatures; and --vv-amber from both copies of tokens.css. Six tests went with them, and the brand spec's 2026-08-27 amendment was replaced by one that returns the palette to two accents.

4.1 · Decisions, and why

  • ①Delete the ramp, do not re-map it. The obvious reading of "orange for 1, lime for 2–4, red for 5–6" was a re-colouring. It was rejected by the owner in favour of lime-only, which also removes the palette conflict the ramp had created: --vv-flare means hazard everywhere else on the same screen, so an easy route and a danger notice would have shared a colour.
  • ②Unselected stays soft rather than grey. The siblings keep the route colour at 2px / 0.4 opacity. A grey sibling reads as a different kind of thing; a dim lime one reads as the same thing, not chosen.

Key takeaways — U0

  • One token, two data-driven expressions: the map's entire colour logic.
  • The deletion reached tokens, the brand spec and the tests — a colour rule is never only in the component.

5 · U1–U2 · The map as a layer P11

Goal. One shell at every width: header, stage, ODbL credit. The conversation is the base layer of the stage and the composer is the app's bottom edge. Tapping a route's card body raises a layer holding the map and that route's card; Escape, browser Back, asking a new question, opening Saved routes or clearing the chat all put it back down. Neither the chat nor the map is ever unmounted — unmounting the chat throws away the transcript of the conversation you are having, and unmounting the map costs its camera and a fresh tile fetch on every open.

Fig. 2 — The two states and every transition between them. Omitted: the Saved-routes sub-state, which is orthogonal — it can be open in either view and is closed by the same events.

5.1 · How the data moves and transforms

A tap enters at the card and leaves as a URL change. The panel and the empty-state text both read from the same two pieces of page state, so they can never disagree about what the map is about.

frontend/app/page.tsx:141–170 — the three functions the whole model rests onP11
/** Raise the map over the conversation, as a history entry. */
function openMap() {
  if (window.location.hash !== '#map') window.location.hash = 'map';
  setView('map');
}

/** Back to the conversation. replaceState rather than history.back(): the
 *  entry we would pop may not be the top one — a Back press is one of the
 *  ways the map closes — and one dead entry is cheaper than the
 *  bookkeeping that would avoid it. ③ */
function closeMap() {
  if (typeof window !== 'undefined' && window.location.hash === '#map') {
    window.history.replaceState(null, '', window.location.pathname + window.location.search);
  }
  setView('chat');
}

function pick(route: Loop | Trail | null) {
  setPicked(route);
  // The detail belongs to the route just picked, not the one before it.
  setRouteDetail(undefined);
  if (route) openMap();
}

The setRouteDetail(undefined) is what makes the panel honest. routeDetail is tri-state: undefined means the fetch is in flight and the card says "Fetching the altitude profile…", null means asked and there is none. Without the reset, a newly picked route would show its predecessor's profile until the fetch landed, or claim "no altitude profile" for a route that has one.

frontend/app/page.tsx:217–222 — what the canvas says when there is nothing on itP11
const emptyNote =
  picked && focusedRouteId(geometry) !== picked.id
    ? 'No map line for this route.'
    : geometry
      ? null
      : 'Nothing drawn yet — pick a route.';

Order matters here: the pick is tested first. A picked route whose line failed to fetch produces no geometry, and "nothing drawn yet — pick a route" would be a lie told to someone who just picked one.

5.2 · Decisions, and why

  • ①Only the card body raises the map. "See more" expands the card in place and draws its line under the closed layer. The rejected alternative — any card interaction raises the map — collapses two gestures into one meaning and makes it impossible to compare two cards' numbers without the map jumping in between.
  • ②The composer is outside both layers. The layer's inset stops var(--vv-composer-h) short of the bottom, so a question can be asked with the map up. Asking then lowers the map, because a count-first answer and its clarify suggestions are read on the conversation. The height is pinned twice — as the variable and as min-height on .composer — so the two cannot drift.
  • ③view is derived from the URL, not from a boolean. Opening pushes #map; a hashchange listener is the only writer of view. Browser Back and Android's back gesture therefore work with no code at all, which was the alternative's whole cost: a boolean plus a popstate handler plus the bookkeeping to keep them in sync. Closing uses replaceState rather than history.back() — the map can be closed from five places and the entry we would pop is not always the top one. The price is one dead history entry.
  • ④inert, not display:none, for the covered transcript. The transcript keeps its scroll position and its selection while the map is over it, but leaves the tab order: reaching a card under the map with Tab and "clicking" it is a gesture with no visible effect.
  • ⑤The panel renders the same card component. Not a summary, not a second implementation — LoopCard with defaultOpen and no onSelect. Without a handler it also stops being a button: a focusable div that does nothing is worse than plain text. The cost is that two elements now share .route-card[data-route-id], so every test locator must be scoped (see R3).

5.3 · For a scalable system

The transcript is one continuous conversation with no windowing: every turn's cards stay mounted, and .messages is a plain overflow-y:auto. At a few dozen turns this is free; at hundreds it is a growing DOM and a slower scrollIntoView. The upgrade is virtualisation of .messages, and it is not due until a real conversation gets long enough to feel it. The map holds one GeoJSON source with every drawn line of the current answer — five to fifty features — which MapLibre restyles rather than refetches when the selection changes.

5.4 · Obligations and edges

No trust boundary moved, but two edges are worth naming. ODbL requires the attribution to be visible on every view that renders map-derived data, never behind a toggle: the shell's credit row is the last row in both states, and the map contributes MapLibre's own attribution row at the canvas foot when it is up — the route panel sits below that row, never over it. location.hash is user-controlled input and now drives a view; it is compared to the literal '#map' and never interpolated into anything, so it is a switch, not a sink.

Key takeaways — U1/U2

  • Two states, one URL-derived variable, five closing paths that all funnel through closeMap().
  • Chat and map are never unmounted; only the favorites view and the panel's card mount.
  • The panel is the transcript's card, given two props — no second rendering of a route anywhere.

6 · U3 · The composer at the bottom edge P11

Goal. Two things move a bottom edge on a phone — the soft keyboard and the home indicator — and both are declared rather than worked around.

frontend/app/layout.tsx:28–33 — the declaration, and what each half buysP11
export const viewport: Viewport = {
  width: 'device-width',
  initialScale: 1,
  viewportFit: 'cover',
  interactiveWidget: 'resizes-content',
};

resizes-content makes the keyboard shrink the layout viewport instead of sliding it, so 100dvh follows the keyboard and the composer stays above it. Chrome and Android honour it; iOS Safari ignores it and moves the visual viewport instead. viewportFit: 'cover' lets the map reach the edges of a notched screen, and the shell pays the insets back as padding — border-box means that eats into the 100dvh rather than adding to it.

frontend/app/globals.css:813–818 — the rule that is not a typographic choiceP11
/* iOS Safari zooms the page in when a focused input's text is under 16px, and
   never zooms back out — the whole layout is left oversized and scrolled. 16px
   on touch is the only thing that stops it; the spec's 13.5px stays wherever
   there is a real pointer. Both inputs, not just the composer: the sign-in
   form is the first thing a phone user focuses. */
@media (pointer: coarse) {
  .composer input,
  .auth input { font-size: 16px; }
}

6.1 · Decisions, and why

  • ①The iOS visualViewport fallback was deliberately not written. It is the one piece of this phase that cannot be tested without a device, and untested compensation code for a browser quirk is how a second quirk gets born. Instead e2e/smoke.spec.ts gained a "what this suite cannot see" checklist naming the exact symptom that makes it due.
  • ②The 16px rule covers the sign-in form too. The plan named only the composer; the same defect applies to the first field a phone user ever focuses. Fixing the class of bug rather than the reported instance is cheaper than fixing it twice.

Key takeaways — U3

  • Both viewport behaviours are declared in one export; the CSS only pays back what the declaration opts into.
  • What can't be verified here is written down as a device checklist instead of guessed at in code.

7 · E0 · The log that names the entry E0

Goal. Make one run answer "which question changed?", and make a single entry re-runnable without paying for the other forty-nine.

7.1 · How the data moves and transforms

backend/scripts/eval_golden.py:75–88 — the selector, and the failure it refusesE0
def select(entries: list[dict[str, Any]], only: str | None) -> list[dict[str, Any]]:
    """The entries this run covers.

    An id that is not in the dataset is a typo, and a typo that silently ran
    zero entries would print a clean 0/0 and read as a pass.
    """
    if not only:
        return entries
    wanted = [part.strip() for part in only.split(",") if part.strip()]
    known = {entry["id"] for entry in entries}
    unknown = [name for name in wanted if name not in known]
    if unknown:
        raise SystemExit(f"--only: no such entry id: {', '.join(unknown)}")
    return [entry for entry in entries if entry["id"] in set(wanted)]

Two accumulators ride alongside the counters through the run loop. Decomposition problems land under plan:, answer problems under answer: on the same entry, so one map distinguishes drift in the intent layer from drift in the prose layer without re-running anything. Retrieval marks are keyed by entry and block, because a single entry may pin both trails and loops and "g30 missed" would not say which half.

backend/scripts/eval_golden.py:326–334 — assembling the line, and the one case that is not loggedE0
# Last, so the aggregates stay at the head of the line where a human reads
# them; the maps are what you grep once a number has moved.
summary["failed"] = failed
if args.graph:
    summary["retrieval"] = retrieval_marks
if args.only:
    print("\n--only: partial run, not appended to eval_runs.jsonl")
    return
log_run(summary)

The same branch corrected a comment that had misdirected the previous reader: the estimate_loops template documented itself as feeding a chat/narrowing.py that was never written. The template is live — chat/orchestrator.py:493 calls it with facet_cap=0 — so the rows are not collected and the count is what reaches the answer as total_loops. The comment now says that.

7.2 · Decisions, and why

  • ⓐAn unknown id stops the run. The alternative — filter to nothing and report 0/0 — is a green run that measured nothing, which is the single worst thing an eval can print.
  • ⓑPer-entry detail on the same line, not a second file. The eval doc's decision ⑥ made the run log a committed artefact so git log answers "what did this prompt change cost". A second file would need its own retention story and could fall out of sync; one line means tail -2 is the whole diff tooling.
  • ⓒ--only does not log. A partial total in the trend is worse than a gap in it: a 2/2 line and a 50/50 line are indistinguishable once they are both just "decomposition". The docstring and CLAUDE.md now say "every FULL run".

7.3 · For a scalable system

The run is serial: ~110 OpenAI calls, about five minutes for 50 entries with --graph --answers. The upgrade path is asyncio.gather with a semaphore, and the eval doc puts it past ~200 entries. The line grows with the failure count, which is bounded by the dataset — a fully failing 50-entry run writes a few KB.

7.4 · Security

The run log is committed to git, so what goes into it is a disclosure decision, not just a format one. Today it carries dataset ids and checker strings; one of those, f"link in answer: {link!r}", embeds a fragment of model output. That is harmless while every input is a repo fixture. It stops being automatic when Phase 8 E2 lands and feedback-born entries carry real user phrasing — see R5.

Key takeaways — E0

  • One line per full run still, now with failed{} and retrieval{} after the aggregates.
  • --only makes a rerun cheap and refuses to pollute the trend.
  • Four new offline tests pin the selector, including the typo case.

8 · What only a browser could tell us

The unit tests and the type checker passed on the first build of the shell. The layout was still broken in two different ways, and both came from the same mechanism: a transformed element still contributes to its ancestors' scrollable overflow. The closed map layer is translated a full height down, and that phantom box has to be clipped by something — the question is by what, and hidden is the wrong answer.

Fig. 3 — The same layer, three clipping choices. Only the third leaves the transcript as the single scroll container.

frontend/app/globals.css:85–92 — the fix, with the reason it is not hiddenP11
/* The closed map layer is translated a full height DOWN, and an absolutely
   positioned child that sticks out counts as scrollable overflow: without
   this the document grew to ~1013px on a 640px screen and scrolled the
   header off the top. `clip`, not `hidden`: hidden still makes this a
   SCROLL CONTAINER, so the transcript's scrollIntoView scrolled the stage
   itself and dragged the whole conversation up by 427px. clip cannot be
   scrolled at all, which leaves .messages the only scroller — as intended. */
overflow: clip;

Neither state would have failed a unit test: jsdom has no layout, and no assertion in the suite asks where the header is. The lesson is narrow and worth keeping — a layout change is not verified until something has laid it out. The verification that caught both was five minutes of driving the real page and reading getBoundingClientRect().

Key takeaways

  • transform does not remove a box from its ancestors' scroll area; something must clip it.
  • overflow: hidden clips and creates a scroll container; clip only clips.
  • Both bugs were invisible to 116 green tests and a clean type-check.

Discovered while writing:

  1. The e2e suite has never run against this shell. Every assertion about the map layer, the route panel, Escape and Back was written blind, and the sign-in assertions changed too (the header's e-mail block became the Sign out button's title). It is the single largest unverified artefact of the session, and it needs the full local stack plus E2E_EMAIL/E2E_PASSWORD. Run it before this branch merges.
  2. Two things wait on a real device. The (pointer: coarse) rule and interactiveWidget cannot be exercised by headless Chromium; the checklist in frontend/e2e/smoke.spec.ts's header names the symptoms. If the composer ends up under the iOS keyboard, the visualViewport fallback becomes due.
  3. Two elements now share .route-card[data-route-id]. The panel renders the same component as the transcript, so an unscoped page.locator('.route-card').first() silently re-resolves to the panel after a click. The e2e was updated to scope every locator to .messages, .favorites-view or .route-panel; the next test written against a card must do the same. A data-surface attribute would make the trap structural rather than remembered.
  4. A trail's GeoJSON does not carry the id the map compares against. focusedRouteId reads route_id ?? id, and the backend's trail features carry trail_id only — so a correctly drawn trail read as "no line for this route" until selectTrail started stamping id client-side. That stamp is a patch on the reader; the cleaner fix is for /trails/{id}/geojson to emit an id property like the route endpoint does.
  5. The committed run log will start carrying user phrasing. Today failed{} holds checker strings over repo fixtures, one of which quotes model output. When E2 turns real downvotes into fb- entries, the same field will quote text a user typed — into a file that is committed and pushed. Decide the redaction rule when E2 lands, not after.
  6. components/MapChrome.tsx now exports only ElevationProfile: the panel it was named for went with the two-pane layout. Accepted, because the rename is a pure churn commit that would touch two importers; do it the next time the file is edited for a real reason.
