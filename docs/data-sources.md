# Data Sources

get-out-door combines two data sources with complementary strengths and weaknesses.

---

## OpenStreetMap (OSM)

### What we use it for

OSM is the source of truth for **physical geography**:

- Trail and road segments (`highway=path`, `highway=track`, `highway=cycleway`)
- Surface information (`surface=unpaved`, `surface=gravel`, etc.)
- Points of interest: lakes, mountain huts, campsites, train stations, bathing spots
- Intersection topology (which paths connect to which)

### Access method

We use the **Overpass API** to fetch data for a configurable bounding box.

```python
# Example Overpass query (generated by osm_ingest.py)
[out:json][timeout:60];
(
  way["highway"~"path|track|cycleway|footway"](bbox);
  node["natural"="water"](bbox);
  node["tourism"="alpine_hut"](bbox);
  node["railway"="station"](bbox);
  node["amenity"="swimming_area"](bbox);
);
out body geom;
```

Alternatively, the `pyrosm` or `osmnx` libraries can parse a local `.osm.pbf` extract for offline or large-area ingestion.

### OSM tags mapped to node properties

| OSM tag | Graph property |
|---|---|
| `highway=path` | `Segment.highway_type = 'path'` |
| `surface=gravel` | `Segment.surface = 'gravel'` |
| `natural=water` | `POI.type = 'lake'` |
| `tourism=alpine_hut` | `POI.type = 'hut'` |
| `railway=station` | `POI.type = 'station'` |
| `amenity=swimming_area` | `POI.type = 'bathing_water'` |

### Limitations

- OSM data quality varies by region. Remote areas may have incomplete trail coverage.
- OSM does not carry curated difficulty ratings for trails (see Trailforks below).
- Segment geometries can be fragmented: one physical trail may appear as dozens of short OSM ways.

## Trailforks

### What we use it for

Trailforks is the source of truth for **trail metadata**:

- Named, curated trail loops (`(:Trail)` nodes)
- Difficulty ratings (`Easy`, `Intermediate`, `Difficult`, `Pro`)
- Trail descriptions (used for vector embedding in Phase 3)
- Community-reported conditions

### Access method

The Trailforks REST API requires an API key. During development, a **mock fixture** (`fixtures/trailforks_mock.json`) is provided to simulate API responses without a key.

```python
# Production (requires TRAILFORKS_API_KEY in .env)
python ingestion/trailforks_ingest.py --bbox 45.8,9.3,46.0,9.6

# Development (uses local mock)
python ingestion/trailforks_ingest.py --mock
```

### Mock fixture format

```json
[
  {
    "trail_id": "tf_001",
    "name": "Lago Loop",
    "difficulty": "Intermediate",
    "total_distance_km": 12.4,
    "description": "A scenic intermediate loop around the lake with some technical singletrack.",
    "geometry": {
      "type": "LineString",
      "coordinates": [[9.38, 45.91], [9.39, 45.92], "..."]
    }
  }
]
```

### Limitations

- API rate limits apply on the free tier.
- Trailforks coverage is excellent for mountain bike trails but thinner for hiking-only routes.

## The Matching Problem

**Trailforks geometries are not the same as OSM geometries.** Even for the same physical trail, the two sources will have:

- Different numbers of coordinate points
- Slight GPS drift (often 5–30 metres)
- Different segment boundaries

### Our approach: spatial proximity linking

We do **not** attempt to merge nodes from both sources. Instead, `spatial_match.py` runs a proximity check:

> If a Trailforks route polyline passes within **20 metres** of an OSM `(:Segment)`, create a `[:MAPS_TO]` relationship.

This is fast, predictable, and failure-safe. A missed match means the trail is not linked to that segment — it does not corrupt the graph.

The threshold (20 m) is configurable via `SPATIAL_MATCH_THRESHOLD_M` in `.env`.

See [`docs/fragilities.md`](fragilities.md) for edge cases.
