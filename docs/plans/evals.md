# Phase 8 — Evals (plan drafted 2026-08-28; folds `docs/explain/eval-pipeline.html` §5)

E0–E2 and E5 are pre-launch; E3–E4 start after Phase 9 D4 go-live (the phase number is not a sequence). Doctrine unchanged (eval doc decisions ①–⑥, `:264-293`): one dataset, one checker (`backend/fixtures/golden_questions.json`, `scripts/eval_golden.py`); code checks only until error analysis names the failure modes — an unvalidated judge is worse than a named gap; pins are ids, never names; the raw stream is graded against `_answer_view`; the run log is committed. Every step is a script, never CI. Order is by cost: each step is the cheapest measurement that pays back before the next is worth buying.

- [ ] E2 `feat/eval-feedback-candidates` — the read side of `message_feedback` (`0004_feedback.sql:1-3` names eval review as its purpose; `feedback.py:5-8` promises the join). Since U5 the key is `(user, message, route_id)` (`0006_feedback_route.sql`): `route_id = ''` is the answer-level vote, a non-empty one names the card that did not belong — negative evidence pointing at the retrieval half of a stub, which the message-level vote could never localise. It does not become an `expect_loops` entry by itself: pins stay positive and hand-written, as the rest of this line already says. `MESSAGES` (`dump_conversation.py:45-50`) left-joins `vote, comment, expected, route_id`; `render_message` (`:63-87`) prints them under the assistant turn, tested in `tests/test_dump_conversation.py`. `--downvotes` limits the dump to conversations holding `vote = -1`; `--json` emits one golden-shaped stub per downvote, `{"id": "fb-<message_id[:8]>", "turns": [every earlier user turn], "expect": {}}` — `expect` stays empty on purpose: the owner writes the expectation, the stub saves the transcription; the standing plan via `readback.describe` (`readback.py:214`), result ids, `comment` and `expected` ride along as reviewer context. Upvotes are not read: a thumbs-up on a wrong answer is the case a judge exists for. PII rule *(recommended)*: real user question text may be copied into `golden_questions.json` (`question`/`turns` only), never a user or conversation id, personal details stripped by hand; `fb-<message_id[:8]>` is the only identifier that travels, for provenance (real user vs written).
